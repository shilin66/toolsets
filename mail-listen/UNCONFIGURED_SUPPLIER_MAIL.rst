未配置邮件合并请求与分支重试
--------------------------

新版首次接入使用一次 ``unconfigured_mail_process`` 请求。后端仍保留分类、时间分析、
草稿生成三个逻辑任务及原页面的状态/重试入口；已配置供应商沿用原流程。
流程为共享邮件/附件输入 → 分类 → 按条件并行执行时间分析与草稿生成 → 统一响应。
非割接通知只返回分类；已有草稿的通知只分类和分析时间；功能关闭或发件人被过滤仍只记日志。

在现有 ``messages[0].content`` JSON 中增加两个布尔值，不放 variables：

.. code-block:: json

   {
     "schema_version": 1,
     "task_type": "unconfigured_mail_process",
     "should_generate_supplier_draft": true,
     "should_analyze_cutover_time": true,
     "draft_id": 123,
     "draft_revision": 0
   }

其余邮件字段、request_id、attempt_id、email_records_id 保持原协议。
should_generate_supplier_draft 由自动发现开关及草稿状态共同计算：只有 collecting 且尚无草稿内容时为 true；
生成中、待审核、已启用及生成失败均不自动重生成。只有 true 时传 fixed_field_defaults。
时间分支只取决于时间分析开关；所有分支还必须先满足模型分类为“割接通知”。
分类/时间节点不接收不需要的固定字段默认说明，草稿节点接收完整规则上下文。

统一结果的 result 包含 classification、time_analysis、supplier_draft，各项格式为：

.. code-block:: json

   {
     "classification": {"status": "succeeded", "result": {"mail_type": "割接通知", "needs_review": false, "classification_reason": "本次维护通知"}},
     "time_analysis": {"status": "succeeded", "result": {"analysis_status": "needs_review", "scene": null, "reply": null}},
     "supplier_draft": {"status": "failed", "error": "分支结果无效，请重试"}
   }

上例仅演示分支封装；各 result 内仍须完整满足原分类、时间和草稿校验协议（包括时间判断依据和 assessed_at）。
未执行的分支仅返回 ``{"status":"skipped"}``，后端不新增对应逻辑任务、不显示跳过原因。
AI 节点捕获异常并连接至统一汇总节点；单个分支报错、空响应或无效 JSON 不阻断其它分支。
分类失败时两个后续分支均不运行；分类失败重试重新走合并请求。

后端收到结果后先校验可信关联字段及分类，再对需要的时间/草稿分支分别使用校验与数据库保存点。
某分支无效只把该分支标记失败，其它有效结果照常保存；失败草稿保持 generation_failed，
失败时间分支不产生待审核回复。人工重试继续使用 supplier_config_draft 或 cutover_time_extract，
只请求失败分支，不重跑成功的分类或另一分支，也不覆盖人工编辑/已取消的回复。
网络断开或整个 HTTP 请求超时、完全没有收到结果时，仍按原规则最多自动尝试 3 次。
一次 HTTP 成功响应中的各分支错误由各自重试入口处理，不触发整包自动重跑。

新增 mail_ai_jobs.workflow_context 保存实际发送的布尔值及草稿版本快照，启动时增量迁移。
领取任务的事务会为同一发件人串行安排未配置邮件处理，不同供应商可并发；
候选记录与样本在请求前关联，防止同一供应商同时来信重复生成草稿。
保存时再次检查开关、正式配置及草稿 id/revision，删除草稿后迟到结果或旧邮件重试不能重建它。
重复结果、过期 attempt_id 和已删除邮件仍被原有幂等/删除保护拦截。

.env 的 API_URL、API_TOKEN、API_TIMEOUT 继续沿用。合并请求超时预算为 3 × API_TIMEOUT，
独立重试维持 API_TIMEOUT；租约覆盖请求预算。工作流异常捕获连线依据 FastGPT 原生 source_catch 机制：
https://github.com/labring/FastGPT/blob/main/packages/service/core/workflow/dispatch/index.ts 。
原三个 task_type 仍可用于在途旧任务及独立重试，工作流发布应先于后端重启。

处理范围与规则
--------------

* 已有正式配置的供应商保持现有业务处理，不受新增发件人过滤策略影响。
* 每个监听邮箱首次启动新版代码时，以 INBOX 的 UIDNEXT 建立持久边界。
  若 STATUS 和 SELECT 均未返回 UIDNEXT，则用 ``UID SEARCH UID *`` 查询当前最大现存 UID，
  以其加一作为扫描上界（空邮箱为 1），不将此上界视为服务器实际的 UIDNEXT。
  只接入此边界之后的新邮件，包括已读邮件；重启继续原游标，不历史补录。
  已有游标不会因邮件删除或邮箱清空而回退；UID 查询失败不会初始化或推进游标。
  UIDVALIDITY 仍必须有效且与已保存值一致，缺失或变化时停止增量接入。
* 未配置邮件先保存原文，再按开关与发件人范围登记初步分类任务。
  分类只允许：割接通知、割接改期、割接取消、割接提醒、故障邮件、其它。
* 开启自动发现时，以规范化发件人完整地址汇集供应商候选及邮件样本，跨接收邮箱归并。
  非通知只收集样本；首次通知生成配置草稿。已有生成任务、失败任务、待审核或已发布草稿时，
  后续通知只添加样本，不重新生成、不覆盖人工编辑。失败生成由人工重试原任务。
* 开启时间分析时，每封不同的新通知独立分析整体窗口，已有配置草稿不会阻止分析。
  不做线路提取、线路匹配、上报任务生成。
* 供应商草稿经人工保存、校验、确认启用后，后续新邮件进入正式配置流程。
  旧邮件的来源、分类和分析结果不追溯修改，也不补生成线路任务。

系统配置
--------

以下配置保存在数据库 system_settings，由“系统配置 / 未配置供应商邮件处理”维护：

.. list-table::
   :header-rows: 1
   :widths: 45 15 40

   * - 配置键
     - 默认值
     - 含义
   * - supplier_auto_discovery_enabled
     - false
     - 自动发现、收集分类样本、生成配置草稿
   * - unconfigured_cutover_analysis_enabled
     - false
     - 分析每封未配置供应商割接通知的整体时间
   * - unconfigured_sender_filter_mode
     - all
     - all / allowlist / blocklist 三选一
   * - unconfigured_sender_filter_list
     - []
     - 邮箱或精确域名规则数组

两个开关相互独立。任意开关开启才需要初步分类；收取时未开启的分支不会在后来开启时补跑。
发件人范围是“全部处理 / 仅处理指定发件人 / 排除指定发件人”三选一，使用一份名单，
没有白名单与黑名单优先级冲突。名单忽略大小写，支持 ``noc@example.com`` 和 ``*@example.com``；
域名规则不包含子域名。白名单模式禁止空名单，黑名单空名单表示全部通过。

功能关闭、发件人被过滤、已有草稿、非通知等策略不执行原因只写运行日志。
日志含 account、email_records_id、sender、stage、reason_code，不记录正文或密钥。
不保存跳过原因字段，不通过 API 返回，不在页面显示跳过标记或补处理按钮。
策略变化可使未执行的队列任务进入内部 cancelled 生命周期，此状态不会出现在业务页面。

FastGPT 调用与工作流
-------------------

继续使用现有 .env 中的 ``API_URL``、``API_TOKEN``、``API_TIMEOUT``。
新增任务直接读取 FastGPT 响应，不配置回调地址或回调鉴权。
不新增模型连接配置，不在系统配置中设置紧急阈值。
新调用与旧调用共用一个 FastGPT 工作流入口。

请求保持 OpenAI 兼容结构，``messages[0].content`` 是序列化 JSON 字符串。
保留原有 email_records_id、email_id、subject、sender、content、attachments、attachment_urls、
supplier_name、supplier_can_reply_directly、supplier_cutover_extract_prompt、
supplier_mail_classify_prompt、securityTime 及现有可选字段；增加：

.. code-block:: json

   {
     "schema_version": 1,
     "task_type": "unconfigured_mail_process",
     "request_id": "持久任务标识",
     "attempt_id": "本次执行标识",
     "draft_id": null,
     "draft_revision": null,
     "security_timezone": "Asia/Shanghai",
     "should_generate_supplier_draft": false,
     "should_analyze_cutover_time": true
   }

所有新增任务参数都放 content，不放 variables。
每次调用使用独立 chatId，AI 节点 history=0，避免不同邮件串上下文。
合并请求需要生成草稿时，以及独立 supplier_config_draft 重试时，另传 ``fixed_field_defaults``，
包含当前系统的 top_fields、line_fields 和 time_conversion_rules。默认规则来自 cutover_prompt.py，
随每次调用读取；仅分类/时间分析的请求不传此字段，工作流内部也从分类/时间节点上下文中剔除它。

合并响应的三个逻辑分支及兼容独立重试的任务输出：

* ``unconfigured_mail_analyze``：输出 mail_type、classification_reason、needs_review。
* ``supplier_config_draft``：输出 config、evidence、unresolved_questions；供应商邮箱 email 由服务端锁定为发件人。
  允许草稿未完整，正式发布必须满足现有 SupplierConfigCreate 校验和真实割接通知样本要求。
  模型在 ``config.fixed_field_rules`` 返回按实际邮件判断后改写的完整字段规则，服务端原样保留。
* ``cutover_time_extract``：模型提取 windows、source_timezone、source_time_text、needs_review、reason；
  FastGPT 代码节点计算最终场景、生成回复，输出统一结果信封。

结果信封均为 schema_version、task_type、request_id、attempt_id、email_records_id、result。
这些关联字段由代码节点取自可信输入，不能让模型决定。Python 端再次严格校验字段类型与值。

供应商草稿必须逐项分析 6 个顶层固定字段（carrier_ticket_no、cutover_time、cutover_backup_time、
cutover_timezone、cutover_reason、location）和 4 个线路固定字段（ImpactType、ImpactDateTime、
ImpactDuration、InteruptionsCounts），不能只生成线路自定义字段。
模型依据邮件标题、正文、表格及附件与默认规则比较，在 evidence 中逐项说明判断依据：

* 实际验证默认适用：新模型输出省略该字段覆盖，编辑器继续显示“默认”，证据说明其适用范围。
  标签相同不代表规则可用，还需核对当前通知与历史引用、字段语义、取值边界、冲突来源及缺失行为。
* 默认不适用或不完整：在 config.fixed_field_rules 返回可独立生效的完整提取提示词。
  可修改、删除不适用的默认提取逻辑，并明确来源、优先级、排除项和缺失处理。
  服务端不自动前置或追加默认全文；编辑器显示“已配置”，人工可继续改写或恢复默认。
* 缺少证据：明确标注“未验证”并写入 unresolved_questions，不宣称默认已通过验证。
  能确认的默认缺失处理可以保留，但不能据此推断未来邮件的格式、永久时区、地点或编号规则。

新提示词不再返回 fixed_field_supplements；旧补充合成路径仅兼容旧工作流及在途结果。
模型先输出逐字段 evidence 与 unresolved_questions（均为字符串数组），再输出 config；
fixed_field_rules 只包含判定需要重写的字段，不能一边声明复用默认、一边返回重述规则。
服务端与人工编辑仍兼容空字符串表示恢复默认。
新草稿使用 prompt_mode=auto，省略时服务端补 auto；历史显式 manual 草稿及人工编辑语义保留。
改写仍须遵守输出结构、UTC 转换、枚举及 5 分钟判定阈值，规则不能硬编码本封邮件的值。
例如原文明示单次中断时长而没有起止时间时，应重写 ImpactDuration 以直接读取并转换该值，
同时重写依赖该时长的 ImpactType；不再拼入“缺少起止时间就返回空”的冲突默认要求。
维护窗口不可代替实际中断时长。未知固定字段及非字符串规则会被拒绝。
现有草稿不自动重生成，正式启用前仍由人工审核；无需新增数据库字段或修改原供应商工作流。

草稿的回复邮箱 ``config.reply_email`` 结合当前邮件明确的回复指示生成：

* 当前通知明确要求本次割接回复、确认或反馈至某个邮箱，且唯一确定的目标地址不同于 sender，
  提取该单个纯邮箱地址；去除显示名称、mailto: 前缀和首尾空白，比较地址时忽略大小写及首尾空白。
* 自动通知说明“请勿直接回复”，同时明确提供适用于本次通知的唯一替代客服/维护联系邮箱时，
  区分禁止回复的自动发件箱与替代联系地址；不同于 sender 的替代地址可作为回复邮箱候选。
  evidence 同时引用这两段指示；营业时间限制写入 unresolved_questions，交人工确认。
  无上下文关联的普通签名、无关支持地址仍不提取。
* 无明确回复指示、指定地址与发件人相同，或只是抄送、普通联系人、无关支持/销售/退订地址，返回 null。
  历史引用中的指示不能替代当前通知；签名中若明确指定本次回复邮箱仍可提取。
* 多个候选无法确定唯一优先级、指示冲突、邮箱格式无效或依赖不可读附件时，返回 null，
  在 unresolved_questions 中列出需人工确认的问题；不得拼接多个邮箱或猜测残缺地址。
* evidence 在 10 个固定字段之外另加 reply_email 判断依据，给出位置、简短原文和与发件人的比较结果。
  后端对 AI 返回的非空地址再次校验，并使用原始邮件中的可信发件人做同址归一；不影响人工编辑已有配置。
* 候选地址随草稿供人工审核，正式启用后作为供应商的回复邮箱。null 启用时沿用现有逻辑回退为供应商邮箱，
  不会在生成草稿时直接发送邮件，也不会因后续新邮件自动覆盖已生成草稿。

存储、并发和回复
----------------

新增表 mail_intake_cursors、supplier_drafts、supplier_draft_samples、mail_ai_jobs。
email_records 新增 processing_origin、unconfigured_analysis_json，旧记录默认为 configured。
原文入库与分类入队、分类成功与下游入队、正式配置插入与草稿发布均在事务内完成。
网络请求放在事务外。启动时自动创建表和增量字段，无需历史数据补录。

MainService 管理 2 个 worker。每个任务有持久唯一键和每次执行 attempt_id，使用事务原子认领。
租约为 max(300 秒, API_TIMEOUT × 2 + 60 秒)，进程退出后过期任务可恢复。
网络失败、429、5xx 最多总计尝试 3 次，正常重试间隔为 30 秒、120 秒。
结构不合法的结果直接记为真实失败，页面可人工重试；旧 attempt 的迟到结果被拒绝。
重复结果不生成重复草稿或回复，不恢复已取消回复；网络超时按队列策略重试。

分析结果与回复状态分开保存。紧急/重保/窗口内结果创建 pending 回复，必须人工确认才发送。
确认接口原子将 pending 改成 sending，防止同时点击或重复请求造成重复发送。
SMTP 超时/失败记录 send_uncertain，禁止自动再次发送；需先核对发件箱或服务器投递日志。
进程在 sending 期间退出也不会自动重发，需由维护人员确认实际结果。
取消回复保留时间判断和场景，发送成功也不表示割接已完成。

隔离预览使用的 ``preview_html`` 和附件链接。HTML 预览保留正文、段落和线路表格，
纯文本预览保留换行。预览采用无权限 sandbox iframe 与 CSP，移除脚本、表单、导航、
外部图片等主动内容；原始邮件在数据库中保持不变。HTML 邮件优先显示原文预览。

邮件类型配置中的分类参考样本与列表摘要是不同字段。保存、读取和生成分类提示词时，
完整保留已配置的主题与正文；正文中的 HTML、表格与换行不做截断。

写入“割接通知”样本，避免模型摘要遗漏信息；人工编辑与发布阶段保留审核后的内容。

GET/PUT system/settings 和原割接邮件列表/详情扩展新字段，原 URL 保持不变。

UIDVALIDITY 变化维护
-------------------

邮箱 UIDVALIDITY 与已保存值不一致时，新增量路径暂停并记录错误，不自动重设或扫历史。
先停止监听服务，备份数据库，向邮箱服务器核对当前 UIDVALIDITY 与 UIDNEXT。
维护脚本默认只检查，不连接邮箱、不扫描邮件：

.. code-block:: sh

   python scripts/reset_mail_intake_cursor.py \
     --database /path/to/mail_listener.db --account inbox@example.com \
     --expected-validity 100 --new-validity 200 --uidnext 5000

检查输出后，使用相同参数附加 ``--apply``，将边界设为服务器当前 UIDNEXT，再启动服务。
停机到建立新边界之间已有邮件不会补录；这是维护人员明确选择的新边界。
若新 UIDNEXT 不大于该接收账号已存邮件的最大 UID，脚本拒绝修改，
因为现有唯一键仍是 (email_id, receiver)；必须另行迁移 UID 命名空间，不能强制覆盖旧数据。
